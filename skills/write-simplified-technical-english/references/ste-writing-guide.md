## Purpose and Source Boundary

Use this guide as an original, compact operating profile for ASD-STE100-style work. It does not replace the official standard or its controlled dictionary.

ASD-STE100 Issue 9 was published on January 15, 2025. Before making a formal or current-edition claim, confirm the active issue on the official ASD or STEMG website. ASD provides official access without charge but retains copyright and trademark rights. Do not copy the dictionary, rule wording, or official examples into an output or bundled resource.

## Local Review Status

These project labels communicate the evidence boundary. They are not official ASD conformance or certification categories.

| Status | Use it when | Do not imply |
| --- | --- | --- |
| `STE-aligned` | You applied this working profile but did not verify all words against the applicable dictionary and project terminology. | Full conformance or certification |
| `Source-checked` | You checked the text against a named official issue and named project glossary or termbase. | Independent certification or organizational acceptance |
| `Organization-approved` | The user provides evidence that the responsible organization accepted the text. | ASD endorsement |

For a source-checked result, record the issue, publication date, glossary name or version, scope checked, unresolved terms, and reviewer limitations.

## Source-Preservation Gate

Freeze these elements before rewriting:

- actors and ownership;
- action order and simultaneous actions;
- conditions, exceptions, and negation;
- quantities, tolerances, units, identifiers, and quoted labels;
- hazard level, hazard, and consequence;
- confirmed facts, estimates, hypotheses, and unknowns.

If the source is ambiguous, keep the ambiguity visible or ask for clarification. Do not select a technically convenient interpretation. If the user asks for a draft without questions, mark the ambiguity after the draft.

## Vocabulary Gate

1. Use the official dictionary to check each general word's approved meaning, part of speech, and form when it is available.
2. Use one approved term for each concept. Do not alternate synonyms for style.
3. Get technical nouns and technical verbs from an approved project, company, industry, or subject-field source when possible.
4. Keep an official long technical term unchanged on first use. Introduce a documented short form only when the source or organization permits it.
5. Prefer noun groups of three words or fewer unless the longer group is an official technical term.
6. Preserve UI labels, commands, code symbols, part numbers, legal names, and quoted text exactly. Format them so readers can distinguish them from prose. Do not format an ordinary verb as a named control unless the source identifies it as a label.
7. Mark a word `unresolved` when no authoritative source supports its use. Do not guess that a familiar word is approved.
8. Use American English spelling unless an applicable directive requires a different spelling.

Do not replace an unresolved word mechanically. Change the sentence structure, then verify that the new sentence keeps the same meaning.

## Sentence Controls

Apply these controls to all text:

- Prefer the active voice. Use passive voice in a description only when the actor is unknown or genuinely unimportant.
- Use a direct verb instead of a vague verb-plus-noun construction.
- Prefer simple verb forms. Avoid compound tenses, verbal `-ing` constructions, and phrasal verbs unless an authoritative source permits a technical term.
- Keep the subject, verb, articles, and other words needed for an explicit sentence.
- Do not use contractions, slang, regional expressions, idioms, or decorative jargon.
- Replace an ambiguous pronoun with its noun.
- Use connecting words to make the relationship between sentences explicit.
- Use a vertical list when one sentence would contain a dense sequence or several related items.
- Do not use a semicolon in STE prose.

Use the 20-word procedure limit and 25-word description limit as screening checks. The official standard has specific word-count rules for punctuation, symbols, and other edge cases. Use the current standard for a formal count.

## Procedural Text

- Give a necessary condition before the command that depends on it.
- Write commands in the imperative and make the actor clear from context. Do not add `shall`, `will`, or an actor subject to a direct instruction.
- Put one instruction in each sentence. Keep actions together only when they must occur at the same time.
- If one condition controls multiple actions, put the condition before a vertical list and put one command in each list item. Do not assume that a condition in the first sentence also controls later sentences.
- Scan for coordinated verbs and connectors such as `and` and `then`; split them unless the actions must be simultaneous.
- Keep information out of a note when the reader must perform it as an instruction.
- Preserve the supplied order. Do not optimize the procedure from general knowledge.

## Descriptive Text

- Start with information the reader needs to understand the details that follow.
- Use a consistent key term to connect related sentences.
- Keep one topic in each paragraph.
- Keep a paragraph to six sentences or fewer.
- Preserve whether a cause or result is confirmed, suspected, estimated, or unknown.

## Safety Text

1. Keep the source's safety level. If no level is supplied, mark it as missing instead of selecting one.
2. Start with a clear prohibition, command, or condition.
3. State the supplied hazard or possible result.
4. Put the safety instruction before the related action.
5. Do not add personal protective equipment, thresholds, recovery steps, or consequences that the source does not provide.

## Audit Method

For each finding, record:

- source location or short excerpt;
- category: vocabulary, terminology, verb, sentence, procedure, description, safety, punctuation, or meaning preservation;
- observed problem, without inventing an official rule number;
- proposed revision;
- basis: official issue, project termbase, this working profile, or unresolved;
- whether the revision can change technical meaning and needs subject-matter review.

Before the findings, report verification coverage separately for writing rules, general-word dictionary meaning/part-of-speech/form, and project terminology. Do not let a completed structure check imply that either vocabulary check is complete.

At handoff, list official-standard review and project-terminology review as two separate remaining checks when either one is incomplete.

Apply all applicable writing controls to the proposed revision. Run a final side-by-side check. A shorter sentence is a failure if it changes an actor, action, sequence, condition, measurement, safety consequence, or uncertainty state.

List source gaps separately from vocabulary findings. If the source says that a duration, value, permission, success signal, or other execution fact is unknown, keep that gap explicit in the delivery.
